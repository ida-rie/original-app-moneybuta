# 認証 Cookie 移行 テスト計画書

最終更新日: 2026-04-23

## 1. 目的

この計画書は、認証方式を「`Authorization: Bearer` 中心」から「`HttpOnly Cookie` 中心」へ段階移行する際に、以下を保証するための実施計画です。

- PWA 再起動後もログイン状態が維持されること
- 認証トークンが `localStorage/sessionStorage` に保存されないこと
- 既存機能（クエスト、設定、通知など）に回帰がないこと
- 非認可アクセスやセッション失効時の挙動が正しいこと

## 2. 対象範囲

- 認証/認可
- セッション復元
- ログアウト
- 主要 API（ホーム、クエスト、設定、通知）
- PWA インストール後の起動動作（iOS/Android）

## 3. 対象外（本計画で実施しないもの）

- デザイン/UI 改修の見た目評価
- 通知配信基盤（外部 Push サービス）の可用性試験
- 大規模負荷試験（同時接続・高トラフィック）

## 4. テスト方針

1. 段階移行に合わせて Phase ごとに実施する
2. まず正常系で基本導線を固定し、その後に異常系とセキュリティ観点を確認する
3. ブラウザ確認後に PWA 実機確認（Android → iPhone）の順で実施する
4. 重大不具合（ログイン不可、無認可アクセス許容、データ破壊）は即時ブロッカー扱いとする

## 5. 前提データ

- 親アカウント A / 子アカウント A1
- 親アカウント B / 子アカウント B1（別家庭）
- 当日分クエスト `Q_TODAY`（子A1）
- 前日分クエスト `Q_YESTERDAY`（子A1）
- Push 通知購読の ON/OFF を切り替え可能な状態

## 6. 環境マトリクス

| 区分 | 環境 |
|---|---|
| Web | Chrome 最新, Safari 最新 |
| PWA Android | Android + Chrome（ホーム画面追加） |
| PWA iOS | iPhone + Safari（ホーム画面追加） |
| API 実行 | ローカル or 検証環境（HTTPS 前提） |

## 7. フェーズ別実施計画

### Phase 1: Cookie 化の早期安定化

目的: ログイン維持の安定化とトークンの JS ストレージ排除

### Phase 2: セキュリティ強化

目的: CSRF、アイドル失効、絶対失効の導入確認

### Phase 3: Supabase 公式寄せ後の最終回帰

目的: 暫定互換の撤去後に認証系が一貫して動くことを確認

## 8. テストケース一覧（ID 付き）

### 8.1 認証・セッション（共通）

1. `AUTH-01` サインイン成功
- 手順: 正しい資格情報でサインイン
- 期待: ホームへ遷移し、初期 API が 200

2. `AUTH-02` サインイン失敗
- 手順: 誤ったパスワードでサインイン
- 期待: エラートースト表示、未ログイン状態維持

3. `AUTH-03` 起動時セッション復元（ブラウザ再起動）
- 手順: サインイン後にブラウザを終了し再起動
- 期待: 再ログイン不要でホーム表示

4. `AUTH-04` 起動時セッション復元（PWA 再起動）
- 手順: PWA をタスク終了して再起動
- 期待: 再ログイン不要でホーム表示

5. `AUTH-05` 明示ログアウト
- 手順: ログアウト操作
- 期待: 保護画面へ再アクセス時に `/signin` へ遷移

6. `AUTH-06` セッション失効
- 手順: 失効済み Cookie で保護 API へアクセス
- 期待: `401`、UI は再認証導線へ遷移

### 8.2 ストレージ・Cookie 検証

1. `STG-01` 認証トークンの保存先確認
- 手順: サインイン後に `localStorage/sessionStorage` を確認
- 期待: 認証トークンが存在しない

2. `STG-02` Cookie 属性確認
- 手順: セッション Cookie 属性を確認
- 期待: `HttpOnly`, `Secure`, `SameSite` が設計値どおり

3. `STG-03` ログアウト時の Cookie 削除
- 手順: ログアウト後に Cookie を確認
- 期待: 認証 Cookie が削除されている

### 8.3 API 認可回帰（主要）

1. `API-01` 親Aが子A1データへアクセス
- 期待: `200`

2. `API-02` 親Aが子B1データへアクセス
- 期待: `403`

3. `API-03` 子A1が自身データへアクセス
- 期待: `200`

4. `API-04` 子A1が他家庭データへアクセス
- 期待: `403`

5. `API-05` 未認証アクセス
- 期待: `401` または `/signin` リダイレクト（設計どおり）

6. `API-06` 既存主要 API 正常動作
- 対象: `/api/basic-amount`, `/api/quests`, `/api/settings/initial`
- 期待: いずれも正常応答

### 8.4 PWA 固有回帰

1. `PWA-01` Android インストール後のログイン維持
- 期待: 再起動後もログイン状態維持

2. `PWA-02` iPhone インストール後のログイン維持
- 期待: 再起動後もログイン状態維持

3. `PWA-03` オフライン復帰後のセッション整合
- 手順: オフライン化→オンライン復帰
- 期待: 復帰後に API が再び正常化

### 8.5 セキュリティ（Phase 2 以降）

1. `SEC-01` CSRF トークン無しの更新 API
- 期待: `403` または `419`（設計どおり）

2. `SEC-02` 不正 CSRF トークンの更新 API
- 期待: `403` または `419`

3. `SEC-03` idle timeout 超過
- 期待: 再認証が必要になる

4. `SEC-04` absolute timeout 超過
- 期待: アクティブ利用中でも再認証が必要になる

### 8.6 互換運用確認（段階移行期間のみ）

1. `CMP-01` 旧 Bearer 経路（残している場合）
- 期待: 互換対象 API のみ動作

2. `CMP-02` 互換撤去後の旧経路
- 期待: 正しく拒否される（`401`）

## 9. 実施順序（推奨）

1. `AUTH-*` → `STG-*` → `API-*` を Web で実施
2. `PWA-*` を Android で実施
3. `PWA-*` を iPhone で実施
4. Phase 2 着手時に `SEC-*` を追加実施
5. 互換撤去直前/直後に `CMP-*` を実施

## 10. 判定基準

### Entry（開始条件）

- 対象ブランチがビルド可能
- 必要なテストアカウント/データが用意済み
- 実機（Android/iPhone）が準備済み

### Exit（完了条件）

- 重大不具合（P1）が 0 件
- `AUTH-*`, `STG-*`, `API-*`, `PWA-*` が全 PASS
- Phase 2 以降は `SEC-*` も全 PASS
- 既知不具合は回避策と期限を記録済み

## 11. 不具合優先度

- `P1`: ログイン不能、認可破綻、他家庭データ閲覧、ログアウト不能
- `P2`: 特定端末のみセッション復元失敗、一部 API 失敗
- `P3`: 文言不備、軽微な導線不整合
